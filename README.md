# researcher-type-diagnosis

大学イベント用の「研究者タイプ診断」。9問・3軸から8タイプを判定する静的サイトです。

## 利用方法

`index.html` をブラウザで開くと利用できます。ビルドや依存パッケージのインストールは不要です。
GitHub Pagesでは、このファイルがあるディレクトリを公開元にしてください。サイト内の参照は相対パスです。

## 公開と更新

公開先：<https://ibu-design.github.io/researcher-type-diagnosis/>

GitHubのリポジトリ設定で、Pagesの公開元を `Deploy from a branch`、ブランチを `main`、フォルダを `/(root)` に設定します。
`.nojekyll` により、HTML・CSS・JavaScript・画像をそのまま配信します。
変更をコミットして `main` にpushすると、GitHub側で再公開されます。
公開後は、このPCやローカル確認用サーバーを起動しておく必要はありません。

イベント前にスマートフォンで回答から結果表示まで確認し、終了後は会場案内を更新するか、Pages設定から公開を停止してください。

## 構成

- `index.html`：スタート・質問・結果画面、会場案内、診断についてのダイアログ。
- `style.css`：スマートフォン優先のレイアウト。暫定の配色は先頭のCSS変数で管理。
- `script.js`：`axes`（3軸）、`researcherTypes`（8タイプ）、`questions`（9問）、`answerLabels`（6件法）、`references`（文献）、採点・画面操作。
- `collection.js`：診断タイプ・参加意向の保存通信、送信状態の保持、再送。
- `config.js`：検証済みのApps Script受付URL。認証情報は置きません。
- `backend/Code.gs`：非公開スプレッドシートへの保存受付。公開の読み出し・統計機能はありません。
- `assets/images/`：提供された8タイプのPNGとHWIPロゴ（`logo.png`）。ファイル名・画像はそのまま使用。
- `tests/scoring.test.cjs`：採点の境界値、逆転項目、8タイプと画像の対応などの検証。
- `tests/storage.test.cjs`：結果保存・復元、破損データ、保存拒否・容量不足、削除範囲の検証。
- `tests/collection.test.cjs`：保存入力の検証、重複防止、更新順序、再送・JSONP応答の検証。

## 編集する場所

タイプ名・画像パス・説明文は `script.js` の `researcherTypes` で変更できます。
説明は提示されたキャラクターイメージを用いた仮文です。`shortCatch` は未確定のため `null` とし、画面には表示しません。
参考文献は `script.js` の `references` にまとめています。Wagner（1995）の出版社書誌情報、Bledowら（2026）・Bentleyら（2015）の出版社公開論文を確認し、掲載ページへのリンクを追加しています。Stokes（1997）は初期仕様の書誌情報を維持しています。
大阪大学まちかね祭のヒューマンウェアイノベーション学位プログラムのイベントの一部です。
イベントのキャッチコピーは「あなたの知らない博士の世界」。スタート画面にプログラムの公式サイトへのリンクと提供されたロゴを掲載しています。
最終配色・細かな装飾は未確定です。

## 質問文の位置づけ

初期版は提供された仕様書の質問文を実装したもので、全9問を原論文から直接翻訳したと確認できるものではありません。
現在の質問は先行研究の概念を参考にしたイベント独自の文案です。原尺度の転載・翻訳ではなく、質問文・採点方法・8タイプ分類の信頼性や妥当性は未検証です。

同じ軸でも場面が変わるよう、次の9問に改稿しました。質問数・順番・回答形式・得点の方向・Q2の逆転処理・判定境界・割合計算は変更していません。

| 軸 | 質問の場面 |
| --- | --- |
| 個人 / 協働 | Q1：アイデアを考える、Q2：気になることを調べる、Q3：難しい課題に取り組む |
| 計画 / 試行錯誤 | Q4：初めてのことに挑戦する、Q5：作ったものを改善する、Q6：思ったように進まない |
| 原理追究 / 社会応用 | Q7：身近な不思議を研究する、Q8：新しい発見の先を考える、Q9：研究を紹介する |

Bledowらの論文では計画と試行錯誤は相補的な過程、Bentleyらの論文では基礎と応用を併せ持つ研究も扱われています。本サイトの二極表示はイベント用の相対的な選好の整理であり、両立しない性質だとするものではありません。
改稿前後で同じ測定特性を持つとは扱わず、イベント前に来場者に近い人へ試してもらい、解釈や答えやすさを確認してください。

## 回答と採点

個々の回答は表示中のページのメモリ内だけに保持し、再読み込みで消えます。個々の回答・軸の得点は外部に送信しません。保存受付の設定後は診断タイプと任意の参加意向だけを送信します。
「戻る」や診断についての表示では回答を保持し、「もう一度診断する」で全回答を初期化します。

診断が完了すると、最新1件の3軸の合計得点を `localStorage` の `researcher-type-diagnosis:result` に保存します。再訪時はその得点からタイプと割合を復元し、結果画面を表示します。回答途中の内容、個々の回答、氏名などは保存しません。
再診断を始めても前回の結果は保持し、次の診断が完了した時点で置き換えます。結果画面の「保存結果を削除」で確認後に削除できます。他サイトや他機能の保存データは削除しません。
保存不可・容量不足でも診断は継続でき、結果画面に保存できなかった旨を表示します。破損データ・不正な得点・異なるバージョンの保存データは復元しません。質問の意味や採点の変更時は `resultStorageVersion` を更新してください。

保存期間はアプリ側では設定していませんが、ブラウザのデータ削除・プライベートブラウズ等で失われる場合があります。同じ端末・ブラウザ・公開URLでの利用を前提とし、端末間の同期は行いません。共有端末では利用後に保存結果を削除してください。
`file:` URLでの保存動作はブラウザ依存です。保存の確認にはGitHub PagesまたはローカルHTTPサーバーを使用してください。[localStorageの仕様と制限](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

- I/C：Q1 + (7 - Q2) + Q3
- P/E：Q4 + Q5 + Q6
- F/A：Q7 + Q8 + Q9

各軸3〜10点はI/P/F、11〜18点はC/E/Aです。

結果画面には両側の割合を表示します。C/E/A側は `Math.round((合計得点 - 3) / 15 * 100)`、I/P/F側は `100 - C/E/A側の割合` です。
両側の合計は100%になります。10点は53%対47%、11点は47%対53%です。
これは今回の回答得点を換算した傾向の目安で、能力・適性、集団内の順位、診断の正しさの確率を表しません。

## 会場案内と非公開のデータ保存

結果画面にスクリーンショット保存・スタッフへの提示を案内し、タイプ別の集計結果は会場で紹介予定と記載しています。公開の統計ページ・自動更新・集計APIは作りません。参加意向の集計値も公開しません。

設定後、結果画面に「行くと思う！」「行かないかも…」の2択を表示します。回答は任意で、予約・席の確保・シールの受け取り条件ではありません。外部フォームへの移動はありません。

保存先は主催者所有の非公開Googleスプレッドシートです。次の4列だけを記録します。

| 列 | 意味 |
| --- | --- |
| `record_id` | ブラウザで生成したランダムなUUID。氏名や端末情報からは作りません |
| `type_code` | IPFなど8タイプのコード。対応するキャラクターは `researcherTypes` を参照 |
| `attendance` | `yes`＝行くと思う、`no`＝行かないかも、空欄＝未回答 |
| `revision` | 古い通信で新しい回答を上書きしないための更新番号 |

氏名・メールアドレス・個々の回答・軸の得点・IPアドレスはアプリの表に保存しません。通信サービス側のログ等はGoogleの取り扱いに従います。
診断完了でタイプを記録し、2択の回答時に同じ行を更新します。再診断では最新タイプに更新し、既存の参加意向を保持します。再送は同じID・更新番号を使うので二重登録になりません。別ブラウザ・データ削除・共有端末では実人数と一致しないことがあり、集計件数として扱います。

集計用ID・タイプ・参加意向・送信状態は `researcher-type-diagnosis:collection` に保存します。「保存結果を削除」は端末内の結果表示だけを削除し、集計用データや送信済みの行は削除しません。旧版で保存した結果は、再訪だけで初回送信しません。ブラウザに送信状態を保存できない場合は重複を避けるため送信しません。

通信はApps ScriptのJSONP応答を使い、書き込み完了の応答を受け取ってから保存済みと表示します。ランダムなコールバック名とレコード内容を検証し、25秒以内に確認できなければ再試行を案内します。送信するのはランダムID・タイプ・参加意向・更新番号だけで、個人情報は含めません。失敗しても診断結果は利用できます。

### 初期設定

1. 主催者アカウントでApps Scriptプロジェクトを作り、`backend/Code.gs` を配置します。
2. 所有者がエディタで `setupStorage` を実行し、Googleの権限を確認して承認します。スプレッドシートは新規作成され、共有設定は変更しません。IDはスクリプトプロパティに保持します。今回この手順は完了済みです。
3. ウェブアプリを「実行するユーザー：自分」「アクセスできるユーザー：全員」でデプロイします。公開するのは保存受付であり、スプレッドシート自体は共有・ウェブ公開しません。今回の `/exec` URLを `config.js` に設定済みです。
4. シートの共有が「制限付き」であることを確認します。URLが空または不正の場合は外部送信せず、2択も非表示です。
5. ログインしていないブラウザから保存・回答変更・再送を試し、同じ行が更新されることを確認してから本番利用します。

公開の読み出し口はありませんが、匿名受付そのものは認証された投票ではありません。入力検証・排他処理・更新番号で通常の二重送信を防ぎますが、意図的な大量投稿を完全には防げません。Apps Scriptの利用上限に達すると受付に失敗します。イベント前に想定同時接続数で確認してください。

### 終了後の運用

Apps Scriptのスクリプトプロパティ `ACCEPTING` を `false` にすると新規保存・更新を停止できます。イベント終了後に非公開のバックアップを取得し、必要な保管期間を主催者が決めてデータを削除してください。自動削除や定期集計のトリガーは作成しません。サイトだけ更新してもApps Scriptのデプロイ版は変わらないため、受付コードの変更時は新しいバージョンをデプロイしてください。

[Apps ScriptのWebアプリ](https://developers.google.com/apps-script/guides/web)・[Content Service](https://developers.google.com/apps-script/guides/content)・[利用上限](https://developers.google.com/apps-script/guides/services/quotas)
